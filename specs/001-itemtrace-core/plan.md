# 实施计划：ItemTrace 本地物品追踪核心闭环

**功能目录**：`specs/001-itemtrace-core` | **日期**：2026-06-20 | **规格**：[spec.md](spec.md)

**Git 分支**：当前未由 Spec Kit 钩子创建或切换功能分支；功能目录是本计划的唯一定位依据。

## 摘要

本计划实现 ItemTrace 的本地优先物品管理闭环：用户可记录、查看、编辑、删除、搜索和筛选
物品，并在首页识别最近添加、即将到期和数量为零的待补货物品。第一阶段以单条物品、单个
可选到期日期和文本位置路径为边界；阶段二再引入经过 SDK 核验的系统提醒、图片、服务卡片、
用户偏好和适配增强；阶段三处理批次、阈值型低库存、借还、导入导出和备份恢复。

实现保持单一 `entry` Stage 模块。ArkUI 页面经应用服务、仓储和 DAO 访问 RDB Store；
提醒、图片、扫码与服务卡片通过独立适配接口隔离系统 Kit，避免把未核验 API、权限或配置
直接传播到业务层。

## 分层架构与状态管理

```text
ArkUI 页面与组件
        ↓ 页面状态 / 用例调用
应用 Service（Item、Expiry、Reminder、Image、Scan、Form）
        ↓
Repository（领域对象、查询语义、事务边界）
        ↓
DAO（参数化查询、行映射） ── RDB Store
        ↓
系统 Adapter（仅阶段二/三：提醒、图片、扫码、Form Kit）
```

- **页面层**：仅处理展示、输入、加载/空/错误/成功状态与路由返回；每个页面在离开时释放临时输入。
- **页面状态**：使用 ArkUI 原生状态承载页面短生命周期状态；列表查询条件由 `ItemQuery` 统一表达，
  编辑草稿不得在保存成功前覆盖持久化对象。复杂跨页结果通过路由返回值或刷新信号传递，不新增
  未批准的全局状态库。
- **应用服务层**：`ItemService` 负责创建、编辑、删除、列表、详情和首页摘要；`ExpiryService`
  集中计算到期状态，防止首页、列表、详情出现不同结果。
- **数据层**：`RdbDatabase` 管理初始化、版本和迁移；`ItemDao` 负责表操作；`ItemRepository`
  返回领域结果或标准错误，不把数据库行和异常泄漏到 UI。
- **系统适配层**：`ReminderAdapter`、`ImageSourceAdapter`、`ScanAdapter` 与 `FormSnapshotProvider`
  是接口边界。各 Adapter 的具体 HarmonyOS 实现只能在 SDK 核验任务通过后新增。

## 数据、仓储与迁移设计

详细字段、索引、状态与阶段演进见 [data-model.md](data-model.md)。第一阶段核心决策如下：

- RDB 中仅有 `item` 业务表；`id` 为稳定唯一标识，位置路径和分类为可空文本字段，避免在 MVP
  引入 Location、Category、Batch 等独立表及关联迁移。
- 到期状态是运行时计算值，不持久化，输入为到期日期、提醒天数和当前本地日期。未填写提醒天数
  时有效值为 7；数量为 0 仅表示待补货。
- `ItemRepository` 至少提供创建、按 ID 查询、更新、确认删除、条件列表查询和首页摘要查询语义；
  所有写操作必须在成功提交后才通知 UI 刷新。
- 数据库版本从 1 开始。每次结构变化必须记录迁移编号、前置版本、向前迁移、失败回滚与验证步骤；
  阶段二图片/提醒表、阶段三批次/位置/分类表不得修改 v1 表语义后静默上线。
- Preferences 只在阶段二引入，保存 `defaultReminderDays`、`defaultSort`、`homeSections`、
  `themeMode` 等非敏感偏好。业务记录、图片索引和提醒执行记录不得写入 Preferences。

## 提醒、图片、扫码与服务卡片策略

### 到期状态与提醒调度

1. **阶段一**：每次创建、编辑、列表、详情和首页摘要时由 `ExpiryService` 按当前本地日期计算
   “无到期日期 / 正常 / 即将到期 / 已过期”。默认提前 7 天只影响状态，不创建系统任务或通知。
2. **阶段二调度输入**：物品到期日期、有效提前天数（物品值优先，否则 Preferences 默认值）与用户
   在设置页显式开启的提醒选项。
3. **阶段二调度规则**：保存或编辑后执行“取消旧任务 → 计算提醒日期 → 创建或更新新任务”；
   删除、清空到期日、关闭提醒时取消任务。默认通知时刻为提醒日当地 09:00；若修改后该时刻已过
   但仍未到期，则只在用户确认后立即提醒一次，避免重复打扰；已过期物品不补发系统提醒。
4. **权限和失败降级**：仅在用户开启提醒或确认创建提醒时请求所需系统授权。拒绝、系统不可用或
   创建失败时保留到期状态和首页临期列表，设置页展示不可用原因与重试入口；不得以常驻后台任务
   替代系统提醒。
5. **SDK 门禁**：在实现 `ReminderAdapter` 前验证 HarmonyOS 6.1 的提醒/通知能力、前台/后台
   限制、精确权限名和取消语义；未验证时仅保留接口和应用内降级。

### 图片、扫码与服务卡片

- **图片（阶段二）**：用户点击“选择照片”或“拍摄照片”时才调用 `ImageSourceAdapter`。成功后将
  图片复制到应用管理的本地范围，并在 RDB 关联本地图片标识和最小元数据；取消、拒绝或复制失败
  时保持原照片不变并显示可重试反馈。精确相册/相机 API 和权限由 SDK 核验决定。
- **扫码（阶段二）**：`ScanAdapter` 的输入是用户主动扫描，输出是可选文本结果；结果只预填备注
  或搜索条件，用户确认后才保存。第二阶段不新增物品编码字段；若后续需要持久化编码，必须先建立
  独立规格、数据模型迁移和验收。当前不假定某个 Scan Kit 的 API 或依赖存在；无可用扫码能力时
  仍可手工输入。
- **服务卡片（阶段二）**：`FormSnapshotProvider` 从 Repository 读取只含计数的快照：即将到期数量、
  今日提醒数量和快速新增动作。卡片更新只在应用数据变更和受支持的系统刷新时机触发；不上传数据，
  不显示敏感详情。具体 Form Kit 配置和生命周期在 SDK 核验后加入 `module.json5`。

## 权限、隐私与异常处理

### 权限策略

| 能力 | 请求时机 | 拒绝或不可用时的行为 | 阶段 |
|---|---|---|---|
| 本地 RDB | 不向用户请求运行时权限 | 显示数据库初始化/读写失败，保留输入并允许重试 | 1 |
| 系统提醒/通知 | 用户在设置页开启提醒，或首次确认创建提醒时 | 保留应用内临期状态；不创建后台替代任务 | 2 |
| 相册选择 | 用户点击选择照片时 | 保持无照片或旧照片，允许再次选择 | 2 |
| 相机 | 用户点击拍摄照片时 | 回到编辑页并保留草稿，允许手工继续填写 | 2 |
| 扫码 | 用户点击扫码时 | 显示不可用提示并提供文本输入 | 2 |
| 服务卡片 | 用户主动添加卡片时 | 主应用功能不受影响；不显示敏感物品详情 | 2 |

Phase 0 必须将上表中的精确权限名、Kit 可用性和 `module.json5` 配置与本机 SDK 6.1.1(24)
文档逐项核验。计划不预写权限字符串或包名。

### 异常处理

- `common/error` 定义统一的领域错误类别：输入校验、数据库初始化、数据库读写、数据不存在、
  系统能力不可用、授权拒绝、外部任务创建失败和未知错误。
- DAO 捕获低层错误并保留安全的诊断信息；Repository 转换为用户无关的领域结果；Service 决定是否
  可重试；页面显示中文、可操作的反馈，不暴露文件路径、SQL 或敏感数据。
- 创建、更新和删除失败时，表单草稿或当前列表不应被错误覆盖。删除必须在用户确认后才执行；
  失败时原记录保持可见。
- 写入及任务调度采用先持久化、后派发系统任务的顺序。若阶段二任务派发失败，记录可恢复的失败状态，
  保留业务记录，并在下一次编辑、启动或用户手动重试时协调。

## 复杂度跟踪

当前没有宪章例外。提醒、图片、扫码和服务卡片适配层属于防止未核验系统 API 泄漏的必要边界，
不是额外架构层；若 Phase 0 发现必须新增模块、后台常驻任务、网络服务或未预期权限，必须先在
此处补充例外理由并更新规格。
